เก็บ baseline เดิมที่สร้างใหม่ได้ก่อนอัปเกรด แล้วเปลี่ยน dependency เป็นชุดที่ระบุชัด หากเพิ่ม feature preview พร้อมเปลี่ยน framework จะยังแยกไม่ได้ว่าผลต่างเกิดจากส่วนใด

## ข่าวนี้ยืนยันอะไร

NVIDIA ออก CUDA 13.5 วันที่ 4 พฤศจิกายน 2026 [ตามประกาศหลัก](https://developer.nvidia.com/blog/nvidia-cuda-13-5-brings-nvidia-vera-rubin-ga-support/) พร้อมการรองรับแพลตฟอร์มและเครื่องมือเพิ่มเติม ส่วนคู่มือ RTX Spark เดือนตุลาคม [แหล่งข้อมูลอีกหน้าหนึ่ง](https://developer.nvidia.com/blog/code-test-and-deploy-on-one-machine-with-nvidia-rtx-spark/) อธิบาย stack บน Windows on Arm ซึ่งยังต้องตรวจ build ของงานเราเอง

## manifest ที่แนบกับผล benchmark

ตารางต่อไปนี้เป็นเกณฑ์ที่เราเสนอให้ใช้ตัดสินใจ ไม่ใช่ผลทดสอบที่ Mimir วัด

| รายการ | สิ่งที่ต้องตรึง | ข้อผิดพลาดที่ช่วยแยก |
| --- | --- | --- |
| build target | GPU/CPU architecture และ compiler flags | ใช้ binary หรือเป้าหมายคนละชุด |
| driver | เวอร์ชันและโหมดที่รองรับ | โปรแกรมคาดโหมดจากเครื่องเดิม |
| runtime | toolkit libraries framework และ image digest | เปลี่ยนหลาย dependency โดยไม่มีร่องรอย |
| ชุดวัด | input seed warmup และการตรวจผล | เวลาลดลงเพราะงานหรือผลลัพธ์เปลี่ยน |

## ผ่านความถูกต้องก่อนประกาศว่ารุ่นใหม่เร็วขึ้น

เราเสนอให้รันชุดตรวจผลที่ครอบคลุมเส้นทางสำคัญก่อนจับเวลา จากนั้นใช้ input และวิธี warmup เดิมเพื่อเทียบ throughput กับ latency จด feature ที่เปิดเพิ่มเป็นเงื่อนไขแยก และไม่เรียกส่วนที่เป็น preview ว่าพร้อม production ตาม toolkit ทั้งชุด

บน Rubin ให้ตรวจข้อกำหนด driver mode แทนสมมติว่าใช้ TCC ตามเครื่องเก่าได้ เก็บคำสั่ง build และ manifest เป็น artifact คู่กับผล แล้วเชื่อมเข้า [สมุด benchmark ของ rig](/benchmarks/)
