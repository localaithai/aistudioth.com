## ข่าว Bolt บอกเงื่อนไขวัดเวลาอย่างไร

[NVIDIA เปิด Bolt E4B 4GB วันที่ 23 ตุลาคม](https://research.nvidia.com/labs/nemotron/NVIDIA-Nemotron-3.5-Bolt-E4B-4GB/) พร้อมกราฟคุณภาพเทียบ TTFT ภายใต้เงื่อนไขที่ผู้พัฒนาระบุ กราฟนั้นจึงเป็นผลของชุดทดสอบผู้ผลิต ไม่ใช่ผลของ rig ทุกแบบ

[Model card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-E4B-4GB) แยก precision และตัวเลือก drafter ไว้ การเลือกคะแนนคุณภาพของ precision หนึ่งมาใช้คู่กับเวลาของอีก precision ต้องระบุเงื่อนไขให้ชัด

## จะเขียน latency recipe ที่ทำซ้ำได้อย่างไร

ข้อวิเคราะห์สำหรับ developer คือให้ไฟล์บันทึกตอบได้ว่ารอบไหนเปลี่ยนอะไร กำหนดขอบเขตจับเวลาตั้งแต่ client และเก็บ output เดิมไว้ด้วย แทนการจดเพียงค่าที่ดีที่สุดจากหลายรอบ

| ตัวแปร | สิ่งที่ตรึง | สิ่งที่รายงานแยก |
| --- | --- | --- |
| โมเดล | Revision ไฟล์และ precision | ผลเมื่อเปลี่ยน artifact |
| Runtime | รุ่น build และคำสั่งเปิด | มีหรือไม่มี drafter |
| Prompt | ข้อความ template และขนาด output | กลุ่มบริบทสั้นกับยาว |
| Cache | ขั้นตอนเริ่มใหม่หรือเตรียมใช้ซ้ำ | Cold request กับ warm request |
| เกณฑ์งาน | คำตอบและ tool call ที่ต้องถูก | TTFT เวลาจบงาน และงานที่ไม่ผ่าน |

ใช้ prompt ชุดเดิมเมื่อเทียบสอง configuration และระบุว่ามีคิวหรืองานอื่นรันร่วมอยู่หรือไม่ ถ้าจะวัดเฉพาะตัว engine ให้แยกผลจากการวัดผ่านแอปที่มีขั้นตอนรับส่งข้อมูลของตนเอง

## จะใช้ผล bench ปรับ rig อย่างไร

### เปลี่ยนทีละตัวแล้วเก็บผลที่ไม่ผ่านด้วย

ตรวจความถูกต้องก่อนจับเวลา โดยเฉพาะงานที่ต้องคืนข้อมูลเป็นโครงสร้างหรือเรียกเครื่องมือ จากนั้นรันหลายรอบด้วยวิธีเดิมแล้วดูการกระจาย ไม่เลือกเพียงรอบที่เร็วที่สุด

เมื่อลองเพิ่มบริบทหรือเปิด drafter ให้บันทึกหน่วยความจำและคุณภาพตามไปด้วย หากเวลาเริ่มตอบดีขึ้นแต่เวลาจบงานหรือความถูกต้องแย่ลง ให้แสดงผลนั้นเป็นข้อแลกเปลี่ยน

ใช้[แนวทาง benchmark สำหรับ AI rig](/benchmarks/) แนบ recipe กับผล เพื่อให้กลับมารันซ้ำหลังเปลี่ยนไดรเวอร์ได้ บทความนี้ไม่ได้ยืนยันความเร็วหรือความสามารถภาษาไทยของ Bolt บนเครื่องที่ยังไม่ทดสอบ
