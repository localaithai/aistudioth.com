อย่าเทียบการเปิดโมเดลรอบแรกกับการรันที่มี cache แล้วโดยไม่บอกเงื่อนไข ทั้งสองตัวเลขมีประโยชน์ แต่ตอบคำถามการใช้งาน rig คนละแบบ

## คู่มือและ release บอกอะไร

AMD เผยแนวทาง YOLO บน ROCm วันที่ 26 ตุลาคม 2026 โดยแยกเส้นทาง PyTorch กับ ONNX ผ่าน MIGraphX ขณะที่ release Ultralytics v8.4.171 ก่อนหน้านั้นระบุการเก็บ compiled model ไว้ใช้ซ้ำ วันเผยคู่มือจึงไม่ใช่วันเปิดตัวการรองรับใหม่

## จัดรอบทดลองอย่างไรให้เทียบกันได้

ตารางเป็นข้อเสนอวิธีวัดสำหรับนักพัฒนา ตัวเลขจากเครื่องของตนเองต้องบันทึกแยกจากผลผู้ผลิต

| ช่วงที่วัด | กำหนดอะไรไว้ก่อน | รายงานอย่างไร |
| --- | --- | --- |
| Cold start | cache มีหรือไม่มี | เวลาตั้งแต่โหลดจนพร้อมรับงาน |
| Warm inference | โมเดลและ cache ชุดเดิม | หลายรอบพร้อมค่ากลางและช่วงกระจาย |
| เตรียมข้อมูล | ขนาดภาพและวิธี resize | เวลาก่อนส่ง tensor ให้ backend |
| หลัง inference | ขั้นตอนจัดรูปผล | เวลาจนได้คำตอบที่แอปใช้ได้ |
| ทั้งคำขอ | input และขอบเขตเดียวกัน | เวลารวมที่ผู้ใช้ต้องรอ |

## ต้องล็อกอะไรเมื่อเปลี่ยน backend

ใช้ checkpoint, precision, task และข้อมูลตรวจคุณภาพชุดเดียวกัน แล้วตรวจ execution provider ที่ถูกเลือกจริงก่อนเก็บความเร็ว หากมีการตกไป CPU ผลนั้นควรแยกชื่อให้เห็นในรายงาน

เมื่ออัปเดต runtime หรือเปลี่ยนโมเดล ให้ตรวจว่า cache เดิมยังเกี่ยวข้องกับการทดลองหรือไม่ และเก็บเวอร์ชันกับเงื่อนไขเริ่มต้นไว้พร้อมผลเสมอ การได้รอบอุ่นเร็วไม่ได้พิสูจน์ว่าแอปที่เริ่ม process ใหม่ทุกครั้งจะตอบได้เร็วเท่ากัน

ใช้ [หน้า benchmark สำหรับ rig นักพัฒนา](/benchmarks/) เตรียมรูปแบบผลวัดก่อนปรับสเปก คู่มือเป้าหมายเป็น Linux x86_64 และไม่ได้ยืนยัน Windows หรือ WSL วิดีโอ Ultralytics ที่แนบเป็นบริบทจากงานก่อนหน้า
