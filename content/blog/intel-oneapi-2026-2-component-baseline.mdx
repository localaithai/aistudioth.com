## oneAPI 2026.2 เปลี่ยนฐานทดลองอะไร

[Intel ระบุวันออก Toolkit 2026.2 เป็น 23 ตุลาคม](https://www.intel.com/content/www/us/en/developer/articles/release-notes/oneapi-toolkit/2026.html) ตาราง component จับคู่ compiler 2026.2 กับ oneDNN 2026.1 ที่ต้องดาวน์โหลดแยก จึงไม่ควรใช้เลข Toolkit แทนรุ่นทุกไลบรารี

[Release notes ของ oneDNN](https://www.intel.com/content/www/us/en/developer/articles/release-notes/onednn/2026.html) ระบุรุ่น 2026.1 วันที่ 15 ตุลาคมและมีรายการแก้ความถูกต้อง เป็นข้อมูลตรวจ regression ประกอบการอัปเดต ไม่ใช่ผลยืนยันว่าโค้ดของเราจะเร็วขึ้น

## เก็บ component manifest อย่างไร

ข้อวิเคราะห์สำหรับคนทำ bench คือเก็บฐานที่ยังรันผ่านก่อนเปลี่ยนระบบ ถ้าแก้ compiler ไลบรารี และตัวเลือก build พร้อมกัน จะระบุสาเหตุของผลต่างได้ยาก แยก environment เดิมกับชุดใหม่แทนการเขียนทับ

| สิ่งที่บันทึก | รายละเอียดที่เก็บ | เหตุที่ต้องแยก |
| --- | --- | --- |
| Source | Commit กับตัวเลือก build | รู้ว่าโค้ดและเส้นทางคำนวณเดิมหรือไม่ |
| Compiler | รุ่นและคำสั่งเรียกจริง | ไม่เผลอใช้ binary จากอีก environment |
| ไลบรารี | รุ่น แหล่งแพ็กเกจ และที่โหลด | แยกของติดตั้งเพิ่มกับของในชุด |
| เครื่อง | OS driver และการตั้งค่าอุปกรณ์ | ไม่ให้การอัปเดตระบบซ่อนอยู่ในผล |
| ชุดทดสอบ | Input, precision และเกณฑ์ความถูกต้อง | เปรียบเทียบงานที่มีนิยามเดียวกัน |

เก็บ output ของการตรวจความถูกต้องกับเวลาของแต่ละรอบไว้ด้วยกัน หากต้องเปลี่ยน tolerance ให้เขียนเหตุผลของงาน ไม่ขยายเกณฑ์เพื่อให้รอบที่เร็วกว่าได้ผ่าน

## จะวัดก่อนหลังโดยไม่ปนค่าได้อย่างไร

### ผ่านความถูกต้องแล้วจึงเริ่มจับเวลา

สร้าง binary ของแต่ละชุดจากคำสั่งที่บันทึกไว้ รัน input เดิมก่อน แล้วค่อยวัดเวลาโดยใช้ warm-up และจำนวนรอบเดียวกัน แยกเวลา compile เวลาเตรียมข้อมูล และเวลา kernel ออกตามคำถามที่ต้องการตอบ

ถ้า regression เกิดในบาง shape ให้เก็บกรณีนั้นเป็นตัวอย่างสั้นที่ทำซ้ำได้ แล้วลองเปลี่ยน component ทีละตัวใน environment แยก การย้อนกลับควรคืนได้ทั้งแพ็กเกจและค่าตั้ง ไม่ใช่เพียงเปลี่ยนเลขเวอร์ชันในบันทึก

ใช้[รูปแบบบันทึก benchmark ของ rig](/benchmarks/) แนบ manifest และคำสั่งรันกับผลก่อนหลัง บทความนี้เป็นแนวทางทดลอง ไม่มีผลวัด oneAPI บนเครื่องของ Mimir
