## Part 2 ของ AMD เพิ่มอะไรจาก FP16

[AMD เผยบทสอน FP8 GEMM วันที่ 23 ตุลาคม](https://rocm.blogs.amd.com/software-tools-optimization/rdna-fp8-gemm/README.html) ทดลองบน RX 9070 XT ด้วย ROCm 10.0 โดยใช้ E4M3 สะสมผลเป็น FP32 และยังไม่ใส่ per-tensor หรือ per-row scale จึงเป็นฐาน kernel สำหรับพัฒนาต่อ ไม่ใช่ inference quantized ที่ครบทั้งเส้นทาง

[Part 1 วันที่ 16 ตุลาคม](https://rocm.blogs.amd.com/software-tools-optimization/rdna-fp16-gemm/README.html) เป็นพื้นฐาน FP16 ที่ต่อยอดมา ประเด็นใหม่ของรอบนี้คือรูปแบบข้อมูลและข้อจำกัดเรื่อง scale ไม่ใช่การประกาศ ROCm รุ่นใหม่

## จะทำบันทึกทดลอง FP8 อย่างไร

ข้อวิเคราะห์สำหรับคนเขียน kernel คือกำหนดสิ่งที่ผลทดสอบพิสูจน์ได้ตั้งแต่ต้น การคูณเมทริกซ์ถูกต้องในชุดข้อมูลทดลองหนึ่งยังไม่พิสูจน์ว่าการ quantize น้ำหนักโมเดลรักษาคุณภาพงานปลายทาง

| ชั้นที่ตรวจ | สิ่งที่ระบุในบันทึก | ผ่านเมื่อใด |
| --- | --- | --- |
| Input | ช่วงค่า shape และรูปแบบจัดเก็บ | สร้างชุดเดิมได้อีกครั้ง |
| Precision | ชนิด input accumulator และ output | เทียบ reference ที่ตรงเงื่อนไข |
| Scaling | มีหรือไม่มี scale และใช้ตรงไหน | ค่าที่คืนมาตรงนิยามของการทดลอง |
| ความถูกต้อง | วิธีเทียบและ tolerance ที่มีเหตุผล | ผ่านก่อนนำเวลาไปจัดอันดับ |
| เวลา | Warm-up รอบวัดและต้นทุนแปลงค่า | แยกเวลา kernel จากเวลาทั้งงาน |

เก็บกรณีที่ค่าเล็กมาก ใหญ่มาก หรือใกล้ขอบเขตของรูปแบบข้อมูลด้วย หากต้องเพิ่มขั้นตอนแปลงหรือจัด layout ให้คิดเวลาและหน่วยความจำของขั้นตอนนั้นแยกไว้ ไม่ซ่อนต้นทุนไว้ก่อนเริ่มจับเวลา

## จะเชื่อม kernel bench กับโมเดลจริงอย่างไร

### ขยายขอบเขตทีละชั้น

หลังผลเชิงตัวเลขผ่าน ให้ทดลอง operator ในโมเดลที่ใช้จริง แล้วค่อยวัดทั้งคำขอด้วย input ที่กำหนดไว้ ถ้าต้องเปลี่ยน quantization หรือ scale ให้ตรวจคุณภาพงานใหม่ ไม่ใช้ผลของอีก precision เป็นตัวแทน

รักษา environment เดิมระหว่างแก้ kernel และบันทึกการเปลี่ยนแพ็กเกจเป็นคนละรอบ ควรเก็บผลที่ไม่ดีขึ้นด้วย เพราะช่วยบอกว่า shape ใดต้องใช้ทางเลือกอื่น

อ่าน[แนวทางบันทึก benchmark ของ AI rig](/benchmarks/) เพื่อจัดผลก่อนและหลังให้คนอื่นทำซ้ำได้ บทความนี้ไม่ได้รายงานการวัดบนเครื่องของ Mimir หรือยืนยันความเร็ว LLM จากเวลา GEMM เพียงอย่างเดียว
