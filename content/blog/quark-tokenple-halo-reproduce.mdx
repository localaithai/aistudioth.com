สร้าง manifest ของการทดลองก่อนเปลี่ยนโมเดล แล้วเปลี่ยนทีละตัวแปร การลดขนาดไฟล์เป็นผลด้าน storage ส่วนคุณภาพคำตอบและ latency เป็นผลคนละชุดที่ต้องวัดเพิ่ม

## ข่าวนี้ยืนยันอะไร

AMD เผยผลตาราง per-token ของ Qwen3.8-Flash-Next วันที่ 12 พฤศจิกายน 2026 [ตามประกาศหลัก](https://rocm.blogs.amd.com/artificial-intelligence/quark-qwen-ple/README.html) โค้ดที่เกี่ยวข้องอยู่ใน PR เปิดวันที่ 28 ตุลาคม [แหล่งข้อมูลอีกหน้าหนึ่ง](https://github.com/vllm-project/vllm/pull/64369) จึงต้องเก็บ commit และ patch ที่ใช้จริง ไม่อ้างชื่อ stable release แทน

## manifest สำหรับเทียบ lookup อย่างตรงกัน

ตารางต่อไปนี้เป็นเกณฑ์ที่เราเสนอให้ใช้ตัดสินใจ ไม่ใช่ผลทดสอบที่ Mimir วัด

| ตัวแปร | ค่าที่ต้องบันทึก | เหตุให้ผลเทียบกันไม่ได้ |
| --- | --- | --- |
| น้ำหนัก | model revision และ quantization config | เปลี่ยนทั้งตารางและน้ำหนักพร้อมกัน |
| lookup | โหมดกับไฟล์ตารางที่โหลด | ชื่อโมเดลเหมือนกันแต่ใช้คนละตาราง |
| runtime | commit, patch และ backend | เครื่องหนึ่งใช้โค้ดที่อีกเครื่องไม่มี |
| การวัด | thinking preset seed และชุดงาน | เปลี่ยน sampling หรือขอบเขตโจทย์ |

## แยกการรันได้ ความแม่นยำ และความเร็ว

แนวทางที่เราเสนอคือเก็บผลคำตอบของงาน coding และ parallel tool calls เป็นรายโจทย์ด้วย คะแนนรวมอาจซ่อนลักษณะความผิดพลาดที่ทำให้ workflow ใช้ต่อไม่ได้ สำหรับ latency ให้บันทึก prompt output และภาระเครื่อง ไม่อนุมานจากความยาวคำตอบ

อย่านำเวลาหรือคะแนนจาก hardware คนละชุดมารวมเป็น benchmark เดียว เก็บผลที่ยังทำซ้ำไม่ได้เป็นช่องว่างของการทดลอง แล้วเทียบวิธีจดผลกับ [แนวทาง benchmarks ของ AI rig](/benchmarks/)
