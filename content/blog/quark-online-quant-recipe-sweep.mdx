เริ่มจาก baseline ที่รันได้ แล้วเก็บ config เป็นไฟล์สำหรับแต่ละสูตร ไม่แก้ค่าหลายจุดระหว่างรันโดยอาศัยความจำ เพราะผลที่เร็วขึ้นอาจมาจาก backend หรือ cache ที่เปลี่ยนแทนสูตร quantization

## ข่าวนี้ยืนยันอะไร

AMD อธิบาย Quark online quantization วันที่ 5 พฤศจิกายน 2026 [ตามประกาศหลัก](https://rocm.blogs.amd.com/artificial-intelligence/online_quantization/README.html) ส่วนงาน NVFP4 ไป MXFP4 เดือนกันยายน [แหล่งข้อมูลอีกหน้าหนึ่ง](https://rocm.blogs.amd.com/software-tools-optimization/nvfp4-to-mxfp4/README.html) แสดงตัวอย่าง requantize ตอนโหลดบนชุดที่ระบุ ไม่ได้ทำให้ทุก format มีคุณภาพเท่ากัน

## ผลแต่ละสูตรควรมีคอลัมน์ใด

ตารางต่อไปนี้เป็นเกณฑ์ที่เราเสนอให้ใช้ตัดสินใจ ไม่ใช่ผลทดสอบที่ Mimir วัด

| กลุ่มค่า | ข้อมูลที่เก็บ | เหตุผล |
| --- | --- | --- |
| ต้นทาง | checkpoint revision และไฟล์ที่ใช้ | ยืนยันว่าเทียบจากน้ำหนักเดียวกัน |
| สูตร | precision รายชั้นและ exclusions | เห็นว่าส่วนใดยังใช้ความแม่นยำสูง |
| ระบบรัน | engine build kernel และ flags | ไม่ปนผลจาก runtime คนละชุด |
| ผลวัด | เวลาโหลด memory peak และงานคุณภาพ | สูตรที่ใช้ memory น้อยอาจไม่เหมาะกับโจทย์ |

## คัดสูตรก่อนสร้างเส้นทางใช้งานประจำ

ข้อเสนอของเราคือทดสอบงานที่แพ้การลด precision ได้ง่าย เช่น คำตอบที่มีรูปแบบตายตัวและการเรียกเครื่องมือ แล้วเก็บกรณีไม่ผ่านคู่กับ latency ไม่มีเหตุให้ถือว่าสูตรที่เล็กที่สุดเป็นผู้ชนะก่อนเห็นงานจริง

online ในที่นี้คือช่วงโหลดน้ำหนัก จึงควรจับเวลา reload และการเริ่ม process ด้วย เมื่อเลือกสูตรได้แล้วค่อยกำหนดวิธีเก็บ artifact และรันซ้ำให้ชัด เทียบรูปแบบจดผลกับ [แนวทาง benchmark ที่ทำซ้ำได้](/benchmarks/)
